<objective>
Close the one gap that would let CACHE-02's fix silently miss the default user workflow: extend
`Installer::Use#fast_path?` with a `spm_cache_version` stamp check so an upgrade with an
unchanged host graph still forces one full `gen-proxy` run (RESEARCH.md Pitfall 2). Separately,
implement CACHE-03's `cache clean` orphan-sidecar sweep so a `.provenance.json`/`.shims.json`
sidecar never outlives the `.xcframework` it describes.

Purpose: `spm-cache build`'s rebuild path already reaches SC1 unconditionally (its
`perform_install` has no fast-path short-circuit) -- but the README-documented default command
(bare `spm-cache`, i.e. `spm-cache use`) does, and today that fast path has zero
spm-cache-version awareness. Without this fix, a developer who runs only the default command
after upgrading keeps serving the stale, pre-Phase-9 proxy forever, even though nothing else in
this milestone is broken.

Output: `fast_path?`'s version-stamp gate, `Command::Cache::Clean#sweep_orphaned_sidecars`, and
regression coverage for both (one extended existing spec file, one new spec file).
</objective>

Design decisions this plan makes (not literally spelled out in RESEARCH.md/PATTERNS.md, resolved
here from reading the actual current source this session):

- **`spec/installer_use_fast_path_spec.rb` ALREADY EXISTS** (created by Phase 6, tests
  `fast_path?`'s DIFF-staleness behavior, NOT its version-staleness behavior) --
  09-RESEARCH.md's "no existing spec targets Installer::Use in isolation was found" is stale;
  this session confirmed the file's presence and content. Task 1 EXTENDS this file, it does not
  create a new one, and must update its shared `write_lockfile` helper (currently omits
  `spm_cache_version` from its fixture JSON entirely) so the four pre-existing passing tests
  keep passing unchanged once the new version check is live -- see Task 1's `<action>`.
- **The version check reads a throwaway `Core::Lockfile.new(@config.lockfile_path)` instance,
  never assigns it to `@lockfile`.** Setting the `@lockfile` ivar as a side effect of the check
  would change what `integrate_proxy_into_project`'s `plugin_only_lockfile_urls` sees on the
  fast path (it currently reads `@lockfile&.projects&.each_value` and silently no-ops when
  `@lockfile` is `nil`) -- an unrelated behavior change this plan must not introduce.
- **`sweep_orphaned_sidecars` runs AFTER `cache clean`'s existing `if @all / elsif @targets.any?
  / else` branch**, not before (diverging from PATTERNS.md's literal placement suggestion of
  "after the guard, before the if @all branch"). Placing it after means a NAMED-target removal's
  own now-orphaned sidecar (today `remove_path` only `rm_rf`s the `.xcframework` path itself,
  leaving the sidecar behind) is caught in the SAME `cache clean <target>` invocation instead of
  requiring a second run. For `--all`, the cache dir is already gone by the time the sweep runs,
  so `Dir.glob` on a missing directory returns `[]` -- a harmless no-op, not an error.
</context>
