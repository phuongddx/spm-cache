<objective>
Every per-package build reads back what was actually realized after resolution, compares it
against the intended host pins it was seeded with, reports any drift, classifies the package's
fidelity status (`host-pinned` / `resolution-incompatible`), prints that status inline in
`spm-cache build` output, and records it (plus realized pins, spm-cache version, config, and
destination set) in a `<name>.xcframework.provenance.json` sidecar next to the cached artifact.

This closes FID-03 (drift is read back and reported), FID-04 (a genuinely incompatible package
still builds from source with a distinct, unmaskable status), CACHE-01 (provenance sidecar), and
the build-output half of DIAG-02. Phase 7's `07-01-SUMMARY.md` explicitly left the seeded
`Package.resolved` in place on success "specifically so this phase can diff it against the
post-build file" -- this plan is that diff.

Phase 7's M2 report-only measurement (`08-M2-MEASUREMENT.md`) found 0/17 resolution-incompatible
packages on the reference project -- not a rescope trigger, so this plan proceeds against the
ROADMAP's current scope without redesign.

Purpose: without this, a seeded pin that xcodebuild silently discards and re-resolves (empirically
proven on this machine, Xcode 26.3/Swift 6.2.4 -- `.planning/research/STACK.md` Experiment H3) is
shipped as a cache artifact indistinguishable from a correctly host-pinned one. Seeding without
read-back is strictly worse than today: it manufactures false confidence.
Output: `BuildPipeline.run`'s drift/status/sidecar logic; `Installer::Build`'s threaded `config:`
kwarg; `spec/build_pipeline_provenance_spec.rb`.
</objective>

Design decisions this plan makes (not literally spelled out in CONTEXT.md, resolved here):
- **Single consolidated insertion point in `run`** (RESEARCH.md Pattern 2 / Open Question 2):
  drift read-back, status classification, and provenance sidecar write/cleanup all happen ONCE,
  in `BuildPipeline.run`, right after `perform_build` succeeds -- not duplicated at each of
  `perform_build`'s direct build, `run_with_scheme`, and `copy_prebuilt_binary_target`'s three
  internal call sites. This is simpler/DRYer (Simplicity First) and is what makes Class E
  (`copy_prebuilt_binary_target`) get a correct provenance sidecar with zero special-casing
  (RESEARCH.md Open Question 1): its `output_path` return value flows back through
  `perform_build` into `run` exactly like the other two paths.
- **Status line printed from inside `BuildPipeline.run` itself** (via `Core::UI.info`), not by
  changing `run`'s return contract. `command/pkg/build.rb` also calls `SPM::BuildPipeline.run`
  and treats its return value as a bare path string (`File.exist?(result)`, `"Built: #{result}"`)
  -- changing the contract would force an unrelated, unnecessary edit to that command. Printing
  inside `run` satisfies DIAG-02's "build output" half (the line appears in `spm-cache build`'s
  own stdout stream, ahead of `Installer::Build`'s existing `"  Cached: #{result}"` line) without
  touching `run`'s return type at all.
- **Diff scope is the INTERSECTION of intended and realized pin identities.** `seed!` copies the
  ENTIRE host graph verbatim into `pkg_dir/Package.resolved`; after a real resolve, SwiftPM
  typically narrows the file to this package's own actual transitive closure. An identity present
  in "intended" but absent from "realized" is not drift -- it was simply irrelevant to this
  package's own manifest. An identity present only in "realized" (a dependency this package needs
  that the host app doesn't have) is likewise not drift, since there's no intended value to
  compare against. Only identities present on BOTH sides, with differing pin values, count.
</context>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| xcodebuild/swift package resolve -> pkg_dir/Package.resolved | Local toolchain output, re-read as trusted data by BuildPipeline's read-back logic (no network, no attacker-controlled input) |
| Provenance sidecar (.provenance.json) -> shared/remote cache backend (if configured) | A local artifact that may later be pulled from a shared backend by a different developer/machine (Core::Diagnostics' remote_backend_connectivity check confirms a remote backend is a supported configuration) |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-08-01 | Tampering | `<name>.xcframework.provenance.json` sidecar | medium | mitigate | The sidecar is a REPORTING/diagnostic aid only -- Phase 8 never uses it to gate cache hit/miss (that's Phase 9's CACHE-02, explicitly out of this phase's scope). A malformed/tampered sidecar is parsed tolerantly (rescue JSON::ParserError) and falls back to `not-graph-pinned`, never asserting a false `host-pinned`. |
| T-08-02 | Information Disclosure | Provenance sidecar JSON content | low | mitigate | Sidecar records EXACTLY the four CACHE-01-specified fields (realized pins, spm-cache version, config, destinations) -- no absolute pkg_dir/resolved_pins_file filesystem paths, no usernames, no hostnames, no build timestamps -- since the file may travel through a shared remote cache backend to a different developer's machine. |
| T-08-03 | Denial of Service | Package.resolved read-back parsing | low | accept | Bounded by the same host graph size Phase 6/7 already accept for the same file format; no new unbounded input surface is introduced by this phase. |
</threat_model>
