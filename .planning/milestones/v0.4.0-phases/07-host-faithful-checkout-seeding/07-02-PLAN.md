  <behavior>
    - Config#build_lock_path returns a stable path OUTSIDE sandbox_dir (e.g. a project_dir-level dotfile) so recreate_dirs's `rm_rf(sandbox_dir)` can never delete it while a lock is held on it.
    - Installer::Build#perform_install acquires an exclusive flock on build_lock_path BEFORE calling `super`, holds it across `super` (recreate_dirs + resolve_umbrella_checkouts) AND the entire build loop (every build_single_target call), and releases it in an ensure regardless of outcome (success, StandardError, or Interrupt).
    - Installer::Use#perform_install's non-fast-path branch (the one that calls recreate_dirs) blocks on the SAME exclusive flock before its own recreate_dirs call -- proven with a real two-process contention test: `Process.fork` a child that acquires the lock and sleeps briefly before releasing it; the parent attempts a non-blocking trylock immediately (unavailable while the child holds it) and again after the child exits (available).
    - Installer::Use#perform_install's fast-path branch (no recreate_dirs, no mutation) does NOT acquire the lock -- it has nothing to protect against.
  </behavior>
  <action>
    Add `build_lock_path` to `Core::Config`. In `Installer::Build#perform_install`, open the lock file
    (`File::CREAT | File::RDWR`, never truncate) and `flock(File::LOCK_EX)` before calling `super`; wrap
    `super` plus the build loop in a `begin/ensure` that always `flock(File::LOCK_UN)`s and closes the file
    handle. In `Installer::Use#perform_install`, acquire the identical blocking `flock(File::LOCK_EX)`
    immediately before its `recreate_dirs` call in the non-fast-path branch, release it once that branch's
    work (`recreate_dirs` through `prepare_proxy`) completes. This is a BLOCKING flock, not a non-blocking
    trylock-and-retry -- "defer rather than interrupt" (07-CONTEXT.md) is satisfied by the OS's own
    blocking semantics: a watcher waiting on `flock(LOCK_EX)` simply resumes the instant the build's lock
    releases, with no polling/backoff logic to write or test. No `watcher.rb` edit is needed since
    `regenerate` always routes through `Installer::Use#perform_install`, which is where the guard lives.
  </action>

  <acceptance_criteria>

    - `Installer::Build#perform_install` holds the lock across both `super` and every `build_single_target`
      call, and always releases it, including when a build raises.
    - Fast-path `Use` runs are unaffected: existing `spec/watch_spec.rb` examples pass unmodified.
  </acceptance_criteria>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| clones_dir path -> shell command | A spm-cache-owned, config-derived path interpolated into an `xcodebuild` command string |
| build_lock_path -> filesystem | A lock file whose lifecycle must survive the very `rm_rf` it is meant to guard against |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-07-06 | Tampering | Buildable#build_command's -clonedSourcePackagesDirPath interpolation | medium | mitigate | Single-quote the path exactly as the existing -destination/-project flags already do (the SkeletonView field-bug precedent for unquoted interpolation); clones_dir itself is spm-cache-owned/config-derived, never user-content-derived |
| T-07-07 | Denial of Service | build_lock_path flock held indefinitely by a crashed-but-not-exited process, blocking all future builds/watch cycles | medium | accept | POSIX releases flock automatically on process exit/crash; a hard timeout would risk two processes writing the same checkout concurrently, which is the worse failure this lock exists to prevent -- accepted per D-06 |
| T-07-08 | Tampering (race) | Installer::Use and Installer::Build both mutating the same checkout tree without the lock | high | mitigate | Blocking flock (D-06) around Build's `super` + build loop and Use's non-fast-path branch; closes Pitfall 15 exactly |
| T-07-09 | Tampering | build_lock_path itself deleted by recreate_dirs' rm_rf(sandbox_dir) while held | high | mitigate | build_lock_path is placed OUTSIDE sandbox_dir by construction (Config#build_lock_path), so recreate_dirs can never remove the path a live lock is held on |

</threat_model>
