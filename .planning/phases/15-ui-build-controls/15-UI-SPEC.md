## UI Considerations

Applicable state considerations resolved: 16 covered (explicit), 0 backstop, 0 unresolved — plus 4 dismissed with reasons (categories impossible or degenerate by construction) — authored 2026-09-02 in the ui-consideration-probe taxonomy over elements E1–E3 (controls row E1: form + interactive-control; confirm bar E2: interactive-control + static-content; message slot E3: static-content); the compiled probe engine (ui-consideration-probe.cjs) independently flagged 18 applicable categories on 2026-09-02 — 16 resolved to explicit contract lines above, 2 reconciled into the by-construction dismissals; every covered category resolves to a contract line below.

### Layout contract

Single page, no routing, FOUR panels in the 14 order — Run Log, Cache State, Doctor, Dependency Graph. Phase 15 adds no panel: the controls live INSIDE the Run Log panel, whose output they produce.

The Run Log panel body, top to bottom:

1. **Controls row** (`#build-controls`) — full width, first child of the panel body, above the identity card. Flex row, `sm` gaps, wraps on narrow viewports: `Build` · `Rebuild all` · `Rollback` left; the inline status message slot right-aligned (`margin-left: auto`), muted, Label size, wrapping to two lines max. `sm` margin below (the banner's spacing rhythm).
2. **Confirm bar** (`#build-confirm`) — occupies the row's place when the rollback confirm is armed (the two containers swap via `hidden`, the card/banner/switch pattern). Flex row, warn 10%-alpha fill, `xs`/`sm` padding, 4px radius, `sm` gaps, wraps: bar text (Body size, primary) · `Confirm` (danger) · `Cancel` (quiet). `sm` margin below.
3. The 14 stack unchanged beneath: identity card → `xl` break → stream group (banner · switch notice · stream row) → overlay pills.

Panel header unchanged: `Run Log` title, connection pill, `Recent runs` dropdown. The controls row renders unconditionally — including over the cold `No runs yet` state, where triggering the first build is its purpose.

### Interaction contract

All POSTs ride the SAME per-launch token via the `X-SPM-Token` header (D-04 — same token as GETs, custom headers only; the token never appears in a POST URL, never in a body, never in logs). Envelope shape `{status, data}` as the GETs; 401/403 renders the locked token-invalid page (existing handling, shared). Working endpoint paths per 15-CONTEXT's integration points (exact paths remain planner-discretionary): `POST /api/build` with JSON body `{"scope":"build"}` or `{"scope":"rebuild"}`; `POST /api/rollback` with an empty JSON body. The 409 rejection carries a machine-readable reason the UI never displays.

- **Single shared slot (D-05 + A1):** exactly ONE UI-spawned run at a time — build OR rollback share the server-side spawn slot. A second POST while held → 409 → busy message inline, buttons stay enabled on the clicking tab's error path / stay disabled wherever freshest data already shows the hold. Rationale: one state variable, and an auto-switch yank mid-watch (14's D-04 is unconditional) is never triggered by a queued second mutation.
- **Build click** → all three buttons disable immediately (double-submit guard, existing `.btn:disabled`) → 2xx: row enters in-flight (`Building…`); the spawned run arrives via the existing auto-switch path (D-09) with the `ui` badge — zero new streaming plumbing. 409: busy message, buttons re-enable. Network/HTTP error: the POST-failure template, buttons re-enable.
- **Rebuild all click** → identical, body `{"scope":"rebuild"}`, message `Rebuilding all…`. The card's argv row is how the user verifies which verb ran.
- **Rollback click (D-08)** → the row swaps to the confirm bar; focus moves to `Cancel` (safe default: Enter never destroys; `Tab` reaches `Confirm`). `Cancel` → back to the row, focus returns to `Rollback`. `Confirm` → both bar buttons disable (double-submit guard) → POST → 2xx: bar collapses, row in-flight (`Restoring source mode…`); 409/error: bar collapses, message slot explains. No native dialogs anywhere (none exist in the dashboard).
- **In-flight exit:** the row returns to idle (buttons re-enabled, message cleared) when the spawned run ends — the same facts that flip the card to `✓ success`/`✗ failed`/`! interrupted`. Wiring: `log.js`, which already processes run_end/CP14 for the card and the displayed run's lines, publishes displayed-run milestones as a DOM CustomEvent `spm-run-progress` (`detail.phase` ∈ `waiting` / `active` / `ended`) — the one sanctioned coupling beyond sessionStorage; `app.js` listens. If the user has pinned an older run in the viewer, the ended milestone for the in-flight run may not be observed until the next freshest `/api/runs` (dropdown open) or hello (reconnect) — the 409 busy message backstops any stale-enabled click, and reload is always truth.
- **Waiting flavor (BLD-02/D-06) — lock-derived, never guessed:** while in-flight, the row shows `Waiting for build lock…` from the moment the freshest lock data (`hello` / `/api/runs` `lock.state: 'held'`, or the spawn POST's response envelope if the planner includes a lock snapshot) says the lock is held, AND no later than the displayed run's own `Waiting for build lock…` announce line. It clears to the verb's baseline message on the run's next stream line — the Installer announces ONLY under contention (probe → announce → block) and prints nothing while blocked, so a following line is proof the wait ended (CP10-honest: derived from the run's own log). Holder attribution in `lock_state` names the newest running run — our own — in BOTH the waiting and building states, so the announce line is the only honest discriminator (A2). Rollback gets the identical treatment once BLD-04 wraps its flock.
- **Terminal-held lock, no UI run in flight:** buttons stay ENABLED (D-05 disables only on slot hold). Clicking Build forms a visible queue: spawn accepted → the run's announce line in-stream + the row's waiting message. Never a silent queue, never a pre-emptive dead control (A3).
- **Cross-tab:** every connected tab sees the spawned run (switch event) and the freshest `hello`/`/api/runs` data; a tab that missed the hold clicks into the 409 busy message. No new polling channel, no new timer — the state table's 5s poll in `app.js` remains the dashboard's only timer and carries no controls state.
- **Failure (BLD-03):** the 14 banner chain serves unchanged — non-zero exit banner + `Jump to first error`, err lines highlighted in fail, filter-piercing jump (D-10). The row adds no failure state; buttons re-enable on run end so the immediate retry (including `Rebuild all` after a failed build) is one click.
- **No stop control:** SC text does not require one; cancellation is WEB2-02. The pgroup mechanics (D-02) land server-side so a future stop is possible — the UI ships none.

### Accessibility contract

- Every control is a native `<button>` — DOM-order tabbing (Build → Rebuild all → Rollback; Confirm → Cancel in the bar), Enter/Space activation, no roving tabindex, no ARIA-reinvented widgets.
- `:focus-visible` renders the 2px outline ring on every control (existing `.btn:focus-visible` pattern, extended to `.btn-danger` with the fail color and `.btn-quiet` with accent).
- The confirm swap moves focus to `Cancel` and announces context via the bar's `role="group"` + `aria-label="Confirm rollback"`; cancelling returns focus to `Rollback`. No focus trap — the bar is inline content, not a dialog.
- The message slot is `aria-live="polite"` — busy/waiting/error state changes announce; `display`-swapped via `hidden` so silent initial state never announces.
- Disabled buttons are native `disabled` (existing `.btn:disabled` opacity 0.6); the message slot always explains WHY while any button is disabled mid-flight.
- No color-only encoding: states are words; the destructive fill pairs with the visible words `Rollback`/`Confirm`; the confirm bar pairs its warn fill with full-sentence text.

## Prohibitions (must-NOT — checker and verifier test these)

1. **No new files, no new assets, no framework, no build step, no CDN, no scheme-absolute URLs.** All changes land in the existing `index.html` / `styles.css` / `app.js` (+ the `log.js` progress announcement). The G-13-1 asset-ref class cannot recur — nothing new is referenced.
2. **No innerHTML, insertAdjacentHTML, document.write, or outerHTML.** Every new dynamic string — envelope `{message}` values, run progress — renders through `el()`/`textContent`. Envelope messages are server-authored and treated as untrusted.
3. **No native dialogs.** No alert(), no confirm(), no prompt() — the 409 busy message and the rollback confirm are INLINE (D-05, D-08).
4. **No new polling channel, no new timer, no second EventSource.** Controls state derives from POST outcomes, the existing SSE stream (via the `spm-run-progress` announcement), and existing hello//api/runs data only. The state table's 5s poll remains the page's only timer.
5. **No client clock.** The controls render no timestamps; nothing here may call `Date.now()` (T-13-16 stands).
6. **No stop/cancel button** (WEB2-02 is deferred). No per-package scope picker (Phase 16). No confirm on Build/Rebuild all — Rollback only.
7. **No second mutation token, no query-param token on POSTs** (D-04: same per-launch token, `X-SPM-Token` header only).
8. **No display of raw server 409 reasons or envelope internals** — the busy/error copy is client-pinned; only the POST-failure templates interpolate the envelope `message`.
9. **No silent states.** A disabled button always has (or is one event from having) a message explaining the hold; a rejected click always renders its message inline.

## Assumptions

Points where 15-CONTEXT is genuinely silent or delegates to discretion, resolved most consistent with the shipped 13/14 system and recorded for the checker and planner:

| # | Assumption | Rationale |
|---|------------|-----------|
| A1 | The single spawn slot is SHARED by build and rollback — a rollback POST while any UI-spawned run is in flight gets the same 409 + busy message | D-05 pins "exactly ONE UI build" but not rollback's relation to the slot; 15-CONTEXT lists "spawn-slot data structure" as discretion. One slot = one row state machine, and 14's unconditional auto-switch (D-04) means a queued rollback would yank the view mid-watch — the confusion is worth more than the concurrency |
| A2 | The row's waiting flavor derives from the run's own `Waiting for build lock…` announce line (entry assisted by freshest hello//api/runs lock data; exit on the run's next line) — not from `lock_state` holder attribution | `lock_state` attributes the lock to the NEWEST running run — our own — identically in the waiting and building states, so it cannot discriminate; the Installer announces only under contention and prints nothing while blocked, making the announce + next line the honest signal (CP10: derive from the run log) |
| A3 | No global lock-held indicator anywhere: the waiting state is UI-run-scoped (row message + in-stream line); buttons are NOT disabled merely because a terminal build holds the lock | 14 explicitly deferred the lock-indicator decision to this phase and rendered nothing for `lock`; D-05 disables only on slot hold; SC2's "never a silent queue" is satisfied by the visible queue a click forms. | A4 | The trigger badge renders `ui` (lowercase) — D-03's locked header value; 14's reserved row anticipated `UI` | The verbatim-render rule (14 D-11) makes casing moot on the frontend; the header value is what ships. Recorded so the checker doesn't flag the case difference between the two specs |
| A5 | 14's empty-state copy stands unchanged (`Run spm-cache build to produce the first run log.`) with the enabled Build button directly above | The copy stays true (terminal path); the button is visually adjacent and self-evident; 15's scope guard (BLD-01..04 exactly) argues against churning 14's pinned strings |
